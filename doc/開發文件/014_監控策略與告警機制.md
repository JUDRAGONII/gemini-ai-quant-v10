**文件編號**：OPS-V10.0-002
**版本**：1.0.0
**建立日期**：2026-01-20
**文件狀態**：正式發布

## 第一章：監控策略總覽

### 1.1 監控目標與範疇

AI 投資分析儀 V10.0 的監控策略旨在建立全方位的系統可觀測性，確保系統在 NAS 私有化部署環境中能夠穩定、可靠地運行。監控系統採用 Prometheus 收集指標、Grafana 呈現儀表板，並透過 Alertmanager 發送告警通知，形成完整的可觀測性三支柱（指標、日誌、追蹤）。本策略涵蓋基礎設施層、容器層、應用層與業務層四個監控維度，實現從硬體資源到業務邏輯的全面覆蓋。

監控系統的核心目標包括：及早發現系統異常並預防故障發生、確保 AI 分析服務的可用性與正確性、保障行情數據與宏觀數據的及時更新、追蹤系統效能趨勢以規劃容量擴充、滿足金融軟體的法規審計要求。所有監控資料保留 90 天，支援問題追溯與趨勢分析。

### 1.2 監控架構設計

監控系統採用 Prometheue 與 Grafana 為核心技術棧，部署架構包含以下組件：Prometheus Server 負責定期抓取各服務的指標數據並儲存時序資料庫；Grafana Server 負責從 Prometheus 讀取數據並渲染視覺化儀表板；Alertmanager 負責接收 Prometheus 的告警規則觸發，進行告警分組、靜默與通知派送；各服務透過 Prometheus Exporters 或應用程式內建的 /metrics 端點暴露指標數據。

在 NAS 部署環境中，監控組件以 Docker Compose 方式部署，配置獨立的監控網路。Prometheus 設定抓取間隔為 15 秒，確保能夠捕捉短暫的效能異常。Grafana 的資料來源僅限於本地 Prometheus，避免跨網路依賴。Alertmanager 整合 LINE Notify 與 Email 兩個通知管道，確保維運人員能夠即時收到重要告警。

### 1.3 監控層級定義

本系統的監控策略分為四個層級，每個層級有不同的監控重點與告警閾值設定。第一層為基礎設施層監控，涵蓋 NAS 設備的 CPU、記憶體、磁碟、網路等硬體資源使用情況，以及硬碟健康狀態與溫度監控。第二層為容器層監控，監控各 Docker 容器的運行狀態、資源使用量、重啟次數與健康檢查結果，確保容器化服務的可用性。第三層為應用層監控，監控 API 服務的回應時間、錯誤率、資料庫連線數、Redis 快取命中率等應用程式指標。第四層為業務層監控，監控數據更新任務執行狀態、AI 報告生成結果、數據品質檢查分數等業務邏輯指標。

## 第二章：基礎設施監控

### 2.1 CPU 監控

CPU 監控是評估系統運算負載的關鍵指標。對於 QNAP TS-h973AX-32G 配備的 AMD Ryzen V1500B 四核心處理器，系統設定以下監控指標與告警閾值。系統整體 CPU 使用率監控項目包括：1 分鐘平均負載、5 分鐘平均負載、15 分鐘平均負載、各核心使用率分布。告警閾值設定為：Warning 等級為 CPU 使用率持續 5 分鐘超過 80%；Critical 等級為 CPU 使用率持續 5 分鐘超過 90% 或任何核心使用率超過 95%。

針對 Docker 容器維度的 CPU 監控，系統監控每個容器的 CPU 使用率百分比與 throttling 次数。當容器 CPU 使用率長期維持在配額上限附近時，表示容器 CPU 配額可能不足，需要調整 cpu_shares 或 cpus 設定。Throttling 次数突然增加表示容器被強制降頻，應立即調查原因。監控儀表板提供 CPU 使用率的時間序列圖表，維運人員可切換不同時間範圍（1 小時、6 小時、24 小時、7 天）觀察使用趨勢。

### 2.2 記憶體監控

記憶體監控對於 Docker 容器環境至關重要，記憶體不足會直接導致容器崩潰或效能急劇下降。監控指標包括：已使用記憶體、可用記憶體、記憶體使用率、記憶體使用量變化趨勢、各進程記憶體占用分布。對於部署於 NAS 的系統，總記憶體為 32GB，其中 8GB 供 NAS 基礎運行，24GB 分配給容器化應用。告警閾值設定為：Warning 等級為記憶體使用率超過 75%；Critical 等級為記憶體使用率超過 85% 或可用記憶體低於 4GB。

容器維度的記憶體監控特別關注容器記憶體使用量與記憶體限額的比例。當容器記憶體使用量接近限額時，系統會發出預警告警。對於記憶體密集型服務如 PostgreSQL、Redis、AI Worker，監控儀表板提供專屬的記憶體使用儀表板，顯示記憶體使用量的歷史趨勢與波動規律。異常的記憶體使用量增長可能表示記憶體泄漏，應列入追蹤項目。

### 2.3 磁碟監控

磁碟監控涵蓋儲存空間使用率與硬碟健康狀態兩個面向。儲存空間監控針對三層儲存架構分別監控：NVMe SSD 層（容器與熱數據）、SATA SSD 層（近期數據）、HDD 層（備份與歸檔數據）。告警閾值設定為：Warning 等級為任一層級使用率超過 80%；Critical 等級為使用率超過 90% 或剩餘空間低於 50GB。

硬碟健康狀態監控透過 SMART 技術讀取硬碟的自我診斷數據，監控項目包括：重新分配的扇區數、待處理的扇區數、UDMA CRC 錯誤計數、硬碟溫度、電源開關次數。當 SMART 參數出現警告或臨界值時，系統立即發出告警，提醒維運人員備份數據並準備更換硬碟。對於 RAID 1 陣列，監控系統同時追蹤陣列狀態，當陣列降級時發出嚴重告警。監控儀表板提供各儲存層的容量使用圖表與預測曲線，協助維運人員規劃儲存擴充。

### 2.4 網路監控

網路監控評估系統的網路連線能力與頻寬使用情況。監控項目包括：網路介面流量（入站與出站位元組數）、網路連線數（Established、TIME-WAIT、CLOSE-WAIT）、網路錯誤率（丟包、CRC 錯誤）、DNS 解析延遲。對於雙網路接口配置的 NAS，系統分別監控各接口的流量與狀態，並在儀表板顯示 Link Aggregation 的聚合效能。

在容器網路監控方面，系統監控 Docker 網路的流量統計，追蹤各服務間的通訊量與網路延遲。異常的跨服務流量可能表示數據同步問題或未預期的通訊行為。對於對外提供服務的 Nginx，監控其接受的連線數與處理的請求數，確保服務容量足夠應對用戶請求。告警規則包含：網路錯誤率超過 0.1% 發出 Warning 告警；網路介面流量達到頻寬上限的 90% 發出 Warning 告警。

## 第三章：容器監控

### 3.1 容器運行狀態監控

容器運行狀態監控是確保微服務架構可用性的基礎。系統監控所有 Docker 容器的狀態變化，包括：容器是否正在運行（up）、是否異常退出（exited）、是否正在重啟（restarting）。監控採用 cAdvisor 收集容器運行指標，並透過 Prometheus 定期抓取。告警規則設定為：任一服務容器停止運行超過 1 分鐘發出 Critical 告警；任一容器在 1 小時內重啟超過 3 次發出 Warning 告警。

健康檢查狀態監控針對定義了 HEALTHCHECK 指令的容器，追蹤健康檢查的執行結果。當容器健康檢查連續失敗超過設定次數（預設 3 次），Docker 會標記容器為 unhealthy，監控系統隨即觸發告警。對於依賴外部服務的容器（如需要連接資料庫的 API 容器），健康檢查應包含依賴服務的連線驗證。監控儀表板提供所有容器的健康狀態概覽，異常容器以紅色標示並顯示故障持續時間。

### 3.2 容器資源使用監控

容器資源使用監控追蹤每個容器的 CPU、記憶體、網路與磁碟 I/O 使用情況。cAdvisor 自動發現並監控所有 Docker 容器，收集細粒度的資源使用指標。對於 AI 投資分析儀的各服務，監控重點如下：API 服務容器監控請求處理延遲與記憶體使用；PostgreSQL 容器監控連線數、查詢延遲與緩衝池使用；Redis 容器監控記憶體使用率與 key 數量；AI Worker 容器監控 CPU 使用率與任務佇列深度。

資源配額監控驗證容器實際使用量是否超過 docker-compose.yml 中定義的資源限制。當容器記憶體使用量接近 limits 設定值時發出 Warning 告警；達到 limits 值的 95% 時發出 Critical 告警並可能觸發容器 OOM Killer。資源使用趨勢圖表協助維運人員判斷是否需要調整資源配額，或評估是否需要擴充硬體資源。

### 3.3 Docker 守護進程監控

Docker 守護進程的穩定性直接影響所有容器服務。監控項目包括：Docker 守護進程是否響應（docker info 命令執行結果）、已運行容器數量、已拉取映像檔數量、儲存驅動程序狀態、網路後端狀態。Docker 守護進程異常會導致所有容器受到影響，因此相關告警設定為最高優先級。

儲存驅動程序監控特別關注 overlay2 或 devicemapper 的空間使用情況。當 Docker 儲存空間不足時，無法創建新容器或拉取新映像檔。監控儀表板顯示 Docker 儲存層的使用量與可用空間，並設定 Warning 閾值為使用率超過 80%。網路後端監控檢查 Docker 網路的連通性，當自定義網路出現問題時，跨容器通訊會失敗。

## 第四章：應用監控

### 4.1 API 服務監控

API 服務監控是確保用戶體驗的關鍵。監控指標包括：請求率（每秒請求數）、回應時間分布（P50、P90、P99）、錯誤率（5xx 錯誤比例）、可用端點數量。告警閾值設定為：Warning 等級為 P99 回應時間超過 500 毫秒、錯誤率超過 0.5%；Critical 等級為 P99 回應時間超過 1 秒、錯誤率超過 1% 或 API 服務完全不可用。

依據 API 端點分類監控，系統對不同功能模組的端點設定不同的監控策略。行情數據 API 需確保低延遲，監控重點在回應時間；AI 分析 API 需監控生成品質與 token 消耗；數據寫入 API 需監控資料庫寫入延遲與成功率。Grafana 儀表板提供 API 效能的即時監控视图，並支援依據日期範圍比較不同時期的效能變化。

### 4.2 資料庫監控

PostgreSQL 監控涵蓋連線管理、查詢效能、複寫狀態與儲存使用。連線監控追蹤當前作用中連線數、最大連線限制使用率、閒置連線數與等待中的連線數。連線數接近 max_connections 限制時會觸發告警，建議調高連線池設定或增加連線池大小。查詢監控追蹤慢查詢（超過 100 毫秒的查詢）數量與分布，識別需要优化的查詢語句。

資料庫效能指標包括：緩衝池命中率（目標值超過 99%）、磁碟讀寫延遲、VACUUM 執行狀態、資料庫大小與表大小分布。監控儀表板顯示各資料表的膨脹率，當表膨脹率超過 20% 時建議執行 VACUUM 或 REINDEX。對於資料庫連線管理，系統使用 PgBouncer 作為連線池，監控 PgBouncer 的客戶端連線數、伺服器連線數與事務處理延遲。

### 4.3 快取服務監控

Redis 快取服務監控確保熱數據存取的效能與可靠性。監控指標包括：記憶體使用率、已使用記憶體大小、key 數量與過期 key 比例、客戶端連線數、命令執行延遲。告警閾值設定為：記憶體使用率超過 80% 發出 Warning 告警；超過 90% 發出 Critical 告警並可能觸發記憶體淘汰。

Redis 持久化監控追蹤 RDB 快照與 AOF 日誌的執行狀態。對於配置了 RDB 定期快照的 Redis，需監控快照執行時間與頻率，確保快照能夠在設定的時間窗口內完成。AOF 重寫狀態與檔案大小也是監控重點。Redis 複寫監控（若有主從配置）追蹤主從同步延遲與數據一致性，確保從節點能夠及時同步主節點的數據變更。

### 4.4 AI 推理服務監控

AI 推理服務監控追蹤 AI 模型推理的效能與資源消耗。監控指標包括：模型推理延遲（生成第一個 token 的時間與完整生成時間）、Token 生成速率（tokens per second）、GPU 使用率（如有 GPU 加速）、模型載入時間與記憶體占用。對於 Gemini 與 Groq LLaMA 的 API 調用，監控 API 延遲、token 消耗速率與配額剩餘量。

AI 任務佇列監控追蹤 Prefect 工作流引擎的任務佇列深度、正在執行的任務數與待處理任務數。當佇列深度持續增加時，表示 AI 處理能力不足或數據攝取出現瓶頸。AI 報告生成監控追蹤報告生成的完成率、平均生成時間與生成失敗原因分析。異常的失敗率可能表示模型 API 問題或數據品質問題。

## 第五章：業務監控

### 5.1 數據更新監控

數據更新監控確保行情數據、宏觀數據與籌碼數據能夠及時、完整地更新。監控項目包括：各數據源的更新任務執行狀態、更新完成時間、數據覆蓋率（應更新筆數與實際更新筆數）、數據延遲（最後更新時間距今的時間）。告警規則設定為：數據更新任務失敗發出 Critical 告警；數據覆蓋率低於 95% 發出 Warning 告警；數據延遲超過預期時間窗口發出 Warning 告警。

對於 FRED 宏觀數據，監控每日同步任務是否在下午 4 點前完成；對於台灣政府數據，監控每月 10 日的同步任務是否完成；對於美股行情數據，監控每日收盤後的增量更新是否在凌晨 2 點前完成。數據品質檢查結果也列入業務監控範圍，DataQualityMonitor 類別執行的完整性、準確性、一致性與時效性檢查結果記錄於監控系統。

### 5.2 AI 分析監控

AI 分析監控追蹤 AI 評分生成與報告生成的品質與效能。AI 評分監控項目包括：評分覆蓋率（已生成評分的股票數佔比）、評分生成延遲（數據更新完成到評分生成完成的時間）、評分穩定性（相鄰交易日評分變化的分布）。異常的評分變動可能表示數據問題或模型問題，需要人工審查。

AI 報告監控項目包括：報告生成數量、報告生成成功率、報告生成平均時間、報告 token 消耗量。對於 RAG 增強生成的報告，監控檢索結果的相關性評分，確保檢索到的上下文能夠支持報告生成。AI 引擎的 System Prompt 執行監控追蹤 prompt 模板的版本與執行次數，確保 prompt 變更受控且可追溯。

### 5.3 數據品質監控

數據品質監控是金融軟體可信度的根本保障。系統實作四層數據品質檢測機制，檢測結果透過監控系統追蹤。完整性檢測驗證必要欄位是否齊全，檢測結果以完整性分數（0-100）呈現；準確性檢測驗證數值是否在合理範圍，檢測結果以準確性分數呈現；一致性檢測驗證跨資料來源的數據是否一致，檢測結果以一致性分數呈現；時效性檢測驗證數據是否及時更新，檢測結果以最後更新時間距今的時間呈現。

數據品質告警規則如下：任一品質分數低於 80 發出 Warning 告警；任一品質分數低於 60 發出 Critical 告警；發現嚴重的數據異常（如價格為負值、成交量異常跳增）立即發出 Critical 告警。監控儀表板提供數據品質趨勢圖，維運人員可觀察數據品質的長期變化趨勢。

## 第六章：告警機制

### 6.1 告警分級定義

告警採用三分級制度，分別為 Critical（嚴重）、Warning（警告）與 Info（資訊）。Critical 等級表示系統故障或即將故障，需要立即處理，通知方式為 LINE Notify 即時推播與 Email 發送，處理時效目標為 15 分鐘內響應、1 小時內恢復。Warning 等級表示系統效能下降或存在潛在風險，需要關注並規劃處理，通知方式為 Email 發送，處理時效目標為 4 小時內響應、24 小時內處理。Info 等級為資訊性事件，供日誌分析與趨勢追蹤使用，原則上不主動通知，但可在監控儀表板查閱。

告警分級的判定依據影響範圍與緊急性。影響範圍包括：用戶無法使用功能（影響 2 人用戶的完整功能）、部分功能受限（影響單一模組功能）、無直接用戶影響（僅內部系統異常）。緊急性包括：立即影響服務可用性、需要儘快處理、可延後處理。組合判定邏輯為：影響服務可用性 + 立即影響 = Critical；影響單一模組 + 需要儘快處理 = Warning。

### 6.2 告警規則配置

告警規則定義於 Prometheus 的 alerting rules 配置檔案中，每條規則包含以下要素：規則名稱（alert name）、expr 表達式（觸發條件）、for 持續時間（條件需持續滿足多久才觸發）、labels 標籤（告警分類與優先級）、annotations 註釋（告警訊息摘要）。以下是典型的告警規則範例：

```yaml
groups:
- name: api-alerts
  rules:
  - alert: APIHighErrorRate
    expr: rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.01
    for: 2m
    labels:
      severity: critical
    annotations:
      summary: "API 錯誤率過高"
      description: "API 5xx 錯誤率目前為 {{ $value | humanizePercentage }}"
```

告警規則的持續時間（for）設定用於避免短暫波動觸發告警。對於關鍵告警，持續時間設定為 1-2 分鐘；對於效能告警，持續時間可設定為 5-10 分鐘。告警規則定期檢討與優化，移除誤報率高的規則，補充遺漏的監控項目。

### 6.3 告警通知配置

Alertmanager 負責告警通知的派送管理。通知管道配置包含以下選項：LINE Notify 透過 access token 認證，支援即時推播，適合 Critical 告警；Email 透過 SMTP 伺服器發送，支援附件，適合 Warning 與 Summary 報告；WebHook 可選配 Slack、PagerDuty 等外部系統整合。

告警分組策略將相似的告警歸納為一組，避免短時間內收到大量告警通知。分組依據為：相同警報名稱（alertname）、相同服務（service）、相同嚴重級別（severity）。群組通知包含該群組內所有告警的摘要資訊，詳細資訊可在 Grafana 或 Prometheus UI 查閱。告警靜默（silence）功能可在維護窗口期間暫停特定告警通知，靜默規則需說明原因與有效期。

## 第七章：監控儀表板

### 7.1 系統總覽儀表板

系統總覽儀表板提供系統健康狀態的一頁式總覽，適合維運人員每日巡檢使用。儀表板分為以下區塊：系統狀態摘要區塊以綠色/黃色/紅色燈號顯示整體健康狀態；基礎資源區塊顯示 CPU、記憶體、磁碟、網路的使用率圖表；容器狀態區塊以清單形式顯示所有容器的執行狀態與資源使用；服務可用性區塊顯示各 API 端點的可用性百分比；數據更新狀態區塊顯示各數據源的最近更新時間與狀態；告警摘要區塊顯示未處理的告警數量與清單。

儀表板頂部提供時間範圍選擇器，可切換 1 小時、6 小時、24 小時、7 天、30 天的時間範圍。右上角顯示最後刷新時間，確保監控數據的時效性。儀表板支援全螢幕模式，適合放置於監控大螢幕持續顯示。

### 7.2 效能監控儀表板

效能監控儀表板聚焦於系統效能指標的分析與趨勢追蹤。API 效能區塊顯示請求率、回應時間分布、錯誤率走勢圖；資料庫效能區塊顯示查詢延遲分布、連線數、緩衝池命中率；快取效能區塊顯示記憶體使用率、命中率、key 統計。各區塊提供細節下鑽功能，點擊圖表可查看更細粒度的數據或相關日誌。

歷史趨勢分析功能支援比較不同時間範圍的效能數據。例如比較本週與上週同期的 API 平均延遲，識別效能變化趨勢。長期趨勢圖協助維運人員規劃容量擴充，當資源使用率呈現穩定成長趨勢時，提前規劃硬體升級或服務水平提升。

### 7.3 業務監控儀表板

業務監控儀表板呈現與系統核心功能直接相關的業務指標。數據品質儀表板顯示各類數據（行情、宏觀、籌碼）的品質分數趨勢；AI 分析儀表板顯示評分覆蓋率、報告生成量、token 消耗量；數據更新儀表板顯示各數據源的更新任務執行紀錄與數據覆蓋率。業務指標設定各自的目標值，儀表板以儀表環或進度條呈現當前值與目標值的差距。

警報歷史分析區塊提供告警的統計分析，包括：過去 24 小時/7 天/30 天的告警數量分布、按服務分類的告警數量、按嚴重級別的告警數量、告警處理時間分布。透過告警分析，維運人員可識別系統的薄弱環節，進行針對性優化。

## 第八章：維運流程

### 8.1 日常巡檢流程

日常巡檢是確保系統穩定運行的基本工作。每日巡檢項目包括：查看監控儀表板有無異常燈號、檢查前一日的告警記錄是否已處理、確認數據更新任務是否正常完成、檢視資源使用率趨勢是否有異常。巡檢時間建議安排在每日開盤前（台股 9:00 前），確保當日交易時段系統處於最佳狀態。

巡檢發現問題的處理流程如下：對於 Critical 告警，立即啟動應變流程，聯繫相關人員處理；對於 Warning 告警，記錄於工作清單，安排時間處理；對於 Info 告警，記錄觀察，持續追蹤。巡檢結果應記錄於維運日誌，供日後分析與經驗累積。

### 8.2 效能調優流程

效能調優基於監控數據的長期趨勢分析。當監控發現效能瓶頸時，調優流程包括：瓶頸識別（透過監控指標確定效能瓶頸位置）、原因分析（分析造成瓶頸的根本原因）、方案制定（提出解決方案並評估影響）、實施執行（在維護窗口執行變更）、效果驗證（比較調優前後的效能數據）。

常見的效能調優場景包括：資料庫查詢優化（添加索引、重寫慢查詢）、快取策略調整（調整 TTL、增加快取容量）、容器資源調整（擴大 CPU/記憶體配額）、排程優化（調整數據更新任務的執行時間分散負載）。每次調優作業記錄於技術文件，供團隊學習參考。

### 8.3 告警處理流程

告警處理流程確保每個告警都得到適當的關注與處理。告警接收階段，維運人員收到告警通知後確認告警內容，判斷告警的有效性與緊急程度。告警分類階段，根據告警類型（系統故障、效能下降、數據異常）分類並指派負責人。告警處理階段，負責人排查問題原因，執行修復動作並記錄處理過程。告警關閉階段，確認問題已解決，標記告警為已處理並記錄處理結論。

告警處理時效要求如下：Critical 告警需在 15 分鐘內響應、1 小時內解決；Warning 告警需在 4 小時內響應、24 小時內解決；未在時效內解決的告警需升級處理。告警處理記錄包含：告警時間、處理人員、根本原因、解決方案、預防措施，供團隊學習與流程改進。
