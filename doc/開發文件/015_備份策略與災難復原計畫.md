## 第一章：備份策略總覽

### 1.1 備份目標與原則

AI 投資分析儀 V10.0 的備份策略旨在確保系統數據在硬體故障、人為錯誤、軟體缺陷或外部災害等情境下能夠快速恢復，保障用戶投資分析的連續性與數據完整性。作為專業金融軟體，系統數據包含行情歷史、宏觀指標、投資組合、AI 分析結果等高價值資產，備份策略必須滿足金融業對數據保護的高標準要求。

備份策略遵循以下核心原則：3-2-1 備份原則（3 份副本、2 種儲存媒介、1 份異地備份）、自動化原則（備份任務全自動化執行，減少人為操作失誤）、可驗證原則（每份備份必須可驗證可恢復性）、最小影響原則（備份執行時段避開服務高峰，減少對用戶體驗的影響）、保留期限原則（依據數據類型與法規要求設定保留期限）。本策略支援 RPO（Recovery Point Objective，復原點目標）為 1 小時，RTO（Recovery Time Objective，復原時間目標）為 4 小時以內的多數災難情境。

### 1.2 備份範圍界定

系統備份範圍涵蓋所有需要保護的數據資產。在結構化數據方面，PostgreSQL 資料庫包含所有業務數據，是最重要的備份標的。需備份的資料庫包括 core schema（用戶帳號、權限配置）、market_data schema（行情數據）、analysis schema（分析結果）、alternative schema（另類數據）。資料庫備份採用全量備份與增量備份相結合的策略。

在配置檔案方面，系統配置文件控制所有服務的行為，包括：docker-compose.yml 主配置文件、.env 環境變數檔案、Nginx 配置檔案、Prometheus/Grafana 配置、應用程式配置（如 config.py）。配置檔案納入 Git 版本控制，同時保留編譯後的靜態副本於備份儲存。

在非結構化數據方面，Storage 服務管理的檔案包括：AI 報告 PDF、使用者頭像、上傳的數據檔案。這類數據變動頻率較低，可採用每日全量備份或 rsync 增量同步方式保護。在容器映像層面，客製化 Docker 映像（AI Worker）需留存版本，確保災復時可重建相同環境。

### 1.3 備份架構設計

備份儲存採用三層架構設計，確保數據的多重保護。第一層為本地備份（Primary Backup），備份資料儲存於 NAS 的備份專用 Volume（backup_data，對應 HDD 儲存池），作為每日全量備份與增量備份的目標位置。本地備份提供最快的恢復速度，適合處理一般硬碟故障或誤刪除等常見災難情境。本地備份保留 7 天。

第二層為外接硬碟備份（Secondary Backup），備份資料定期同步至外接 USB 3.2 SSD（至少 2TB 容量）。外接硬碟平時存放於異地（如辦公室保險櫃），每週進行一次同步更新。外接硬碟備份提供對火災、水災等本地災害的保護能力。外接硬碟備份保留 4 週。

第三層為雲端備份（Cloud Backup，選配），可選用 QNAP Cloud Sync 或其他雲端儲存服務（如 Backblaze B2）進行異地備份。雲端備份適合對數據安全性有極高要求的用戶，可設定每日或每週自動同步。雲端備份保留 1 個月。本章後續章節的技術說明以本地備份為主，外接硬碟與雲端備份為輔。

## 第二章：資料庫備份策略

### 2.1 PostgreSQL 備份機制

PostgreSQL 資料庫備份採用 pg_dump 全量備份與 WAL（Write-Ahead Log）歸檔備份相結合的策略，實現 Point-in-Time Recovery（PITR）能力。全量備份透過 pg_dump 命令執行，每日凌晨 3:00 自動執行，產生自包含的 SQL 脚本檔案。備份腳本範例如下：

```bash
#!/bin/bash
# /opt/ai-investor/backup/scripts/pg_backup.sh

BACKUP_DIR="/backup_data/pg_dump"
DATE=$(date +%Y%m%d_%H%M%S)
DATABASE="ai_investor"
DB_USER="postgres"

# 建立備份目錄
mkdir -p ${BACKUP_DIR}/${DATE}

# 執行全量備份
pg_dump -U ${DB_USER} -d ${DATABASE} -Fc -f ${BACKUP_DIR}/${DATE}/full_backup.dump

# 壓縮備份檔案
gzip ${BACKUP_DIR}/${DATE}/full_backup.dump

# 產生 MD5 校驗和
md5sum ${BACKUP_DIR}/${DATE}/full_backup.dump.gz > ${BACKUP_DIR}/${DATE}/checksum.md5

# 清理 7 天前的備份
find ${BACKUP_DIR} -type f -mtime +7 -delete

echo "Backup completed: ${DATE}"
```

WAL 歸檔備份實現連續備份能力。修改 PostgreSQL 配置 postgresql.conf，啟用 WAL 歸檔功能：

```properties
wal_level = replica
archive_mode = on
archive_command = 'cp %p /backup_data/wal_archive/%f'
```

WAL 歸檔目錄 /backup_data/wal_archive 存放所有 WAL 段檔案，支援從任意時間點恢復資料庫狀態。WAL 歸檔檔案保留 7 天，結合每日全量備份可實現最多 7 天內任意時間點的恢復。

### 2.2 備份驗證機制

每次備份完成後，系統執行備份驗證流程，確認備份檔案的完整性與可恢復性。驗證流程包括以下步驟：檔案存在性檢查確認備份檔案已成功建立；檔案大小檢查確認備份檔案大小合理（大於 1MB）；MD5 校驗和比對確認檔案傳輸過程無損壞；pg_restore 測試嘗試使用 pg_restore 模擬恢復，驗證備份檔案語法正確。

備份驗證腳本範例如下：

```bash
#!/bin/bash
# /opt/ai-investor/backup/scripts/pg_backup_verify.sh

BACKUP_DIR="/backup_data/pg_dump"
DATE=$1

if [ -z "$DATE" ]; then
    DATE=$(ls -1 ${BACKUP_DIR} | tail -1)
fi

BACKUP_FILE="${BACKUP_DIR}/${DATE}/full_backup.dump.gz"
CHECKSUM_FILE="${BACKUP_DIR}/${DATE}/checksum.md5"

# 驗證 MD5
if ! md5sum -c ${CHECKSUM_FILE} > /dev/null 2>&1; then
    echo "ERROR: Checksum verification failed for ${BACKUP_FILE}"
    exit 1
fi

# 測試 pg_restore 語法
if ! gzip -dc ${BACKUP_FILE} | pg_restore -l > /dev/null 2>&1; then
    echo "ERROR: pg_restore syntax verification failed"
    exit 1
fi

echo "Backup verification passed for ${DATE}"
exit 0
```

驗證結果記錄於 /var/log/backup/backup.log，驗證失敗時觸發告警通知維運人員。每月第一個週日執行完整恢復測試，將備份恢復至測試環境，驗證實際可恢復性。

### 2.3 備份排程配置

備份任務排程透過 Prefect 工作流引擎管理，配置於 /opt/ai-investor/flows/backup_flow.py：

```python
from prefect import flow, task
from prefect.docker.images import pull_image
import subprocess

@task
def perform_pg_backup():
    subprocess.run(['/opt/ai-investor/backup/scripts/pg_backup.sh'], check=True)

@task
def verify_backup():
    subprocess.run(['/opt/ai-investor/backup/scripts/pg_backup_verify.sh'], check=True)

@flow
def backup_flow():
    backup_result = perform_pg_backup()
    if backup_result:
        verify_backup()

if __name__ == "__main__":
    backup_flow()
```

排程設定如下：全量資料庫備份於每日凌晨 3:00 執行；WAL 歸檔持續執行（由 PostgreSQL 主動觸發）；備份驗證於每日凌晨 4:00 執行；外接硬碟同步於每週日凌晨 2:00 執行；月度完整恢復測試於每月第一個週日執行。

## 第三章：檔案備份策略

### 3.1 配置檔案備份

系統配置檔案透過 Git 版本控制管理，備份策略整合 Git 推送機制。配置檔案清單包括：docker-compose.yml 及相關配置、.env 範本檔案、nginx/ 目錄配置、prometheus/ 目錄配置、grafana/ 目錄配置、app/ 目錄應用配置。配置變更流程為：編輯配置檔案、Git commit 記錄變更、Git push 至備份倉庫。

每日凌晨執行配置檔案的獨立備份，產生 tar.gz 封裝檔案：

```bash
#!/bin/bash
# /opt/ai-investor/backup/scripts/config_backup.sh

BACKUP_DIR="/backup_data/configs"
DATE=$(date +%Y%m%d)
CONFIG_SOURCE="/opt/ai-investor"

mkdir -p ${BACKUP_DIR}

tar -czf ${BACKUP_DIR}/configs_${DATE}.tar.gz \
    --exclude='.git' \
    --exclude='__pycache__' \
    --exclude='.env' \
    -C ${CONFIG_SOURCE} .

echo "Config backup completed: ${DATE}"
```

### 3.2 Storage 資料備份

Storage 服務管理的非結構化數據透過 rsync 工具增量同步備份。同步排程為每日凌晨 5:00 執行：

```bash
#!/bin/bash
# /opt/ai-investor/backup/scripts/storage_backup.sh

SOURCE_DIR="/storage_data"
BACKUP_DIR="/backup_data/storage"
DATE=$(date +%Y%m%d_%H%M%S)

mkdir -p ${BACKUP_DIR}/${DATE}

rsync -av --delete \
    ${SOURCE_DIR}/ \
    ${BACKUP_DIR}/${DATE}/

# 維護最近 7 天快照
rm -rf ${BACKUP_DIR}/$(date -d "7 days ago" +%Y%m%d_%H%M%S)

echo "Storage backup completed: ${DATE}"
```

對於 AI 報告等可重建數據，可選擇性降低備份頻率。若 Storage 資料遺失，系統可透過重新執行 AI 分析任務重建報告，因此 Storage 備份優先級低於資料庫備份。

### 3.3 容器映像備份

客製化容器映像（如 AI Worker）需留存版本，確保災復時可重建相同環境。備份策略為每次映像更新時推送至本地 Registry 並執行備份：

```bash
#!/bin/bash
# /opt/ai-investor/backup/scripts/image_backup.sh

BACKUP_DIR="/backup_data/docker_images"
DATE=$(date +%Y%m%d)

mkdir -p ${BACKUP_DIR}

# 匯出 AI Worker 映像
docker save ai-investor-worker:latest | gzip > ${BACKUP_DIR}/ai-investor-worker_${DATE}.tar.gz

# 列出可用映像版本
docker images --format "{{.Repository}}:{{.Tag}}" > ${BACKUP_DIR}/image_list.txt

echo "Image backup completed"
```

## 第四章：災難復原計畫

### 4.1 災難情境分析

本節識別系統可能遭遇的災難情境，並針對每種情境制定對應的復原程序。災難情境依據發生機率與影響程度分為三類：

第一類為常見災難情境，包括：單一硬碟故障（RAID 1 陣列中一顆硬碟損壞）、容器異常終止（單一服務容器崩潰但 NAS 正常）、資料庫檔案損壞（可透過 pg_dump 備份恢復）。這類情境發生機率較高，復原時間目標為 1 小時以內。

第二類為重大災難情境，包括：RAID 陣列完全故障（兩顆硬碟同時損壞）、NAS 設備硬體故障（主板、電源等關鍵元件損壞）、人為誤操作（誤刪除重要數據或配置）。這類情境發生機率較低，復原時間目標為 4 小時以內。

第三類為極端災難情境，包括：火災、水災等本地災害導致 NAS 設備完全損毀、勒索軟體攻擊導致數據被加密。這類情境極少發生但後果嚴重，復原時間目標為 24 小時以內，需依賴異地備份恢復。

### 4.2 復原程序：單一硬碟故障

當 RAID 1 陣列中一顆硬碟故障時，系統仍可正常運行，但需盡快更換故障硬碟。復原步驟如下：確認故障硬碟槽位（透過 NAS 管理介面或硬碟指示燈識別）、關閉 NAS 電源（或熱插拔支援的情況下直接更換）、移除故障硬碟、安裝新硬碟（相同型號或經認證的相容硬碟）、開機後確認 RAID 重建自動開始、監控 RAID 重建進度（通常需要數小時至數十小時）、重建完成後確認資料完整性。

NAS 管理介面的 RAID 狀態監控指令：

```bash
# 檢查 RAID 狀態
mdadm --detail /dev/md0

# 監控重建進度
cat /proc/mdstat
```

### 4.3 復原程序：資料庫檔案損壞

資料庫檔案損壞的復原流程基於 pg_dump 備份與 WAL 歸檔。假設需要恢復至特定時間點（如誤刪除操作發生的時間）的狀態：

```bash
#!/bin/bash
# /opt/ai-investor/backup/scripts/db_restore.sh

BACKUP_DIR="/backup_data/pg_dump"
WAL_DIR="/backup_data/wal_archive"
RESTORE_TARGET="$1"  # 目標恢復時間點，格式：YYYY-MM-DD HH:MI:SS

# 停止相關服務
docker-compose stop api worker

# 清空損壞的資料庫目錄（危險操作，請先確認）
# rm -rf /var/lib/postgresql/data/*

# 從全量備份恢復
docker run --rm -v pgdata:/data -v ${BACKUP_DIR}:/backup ubuntu:20.04 \
    bash -c "cd /data && cat /backup/<backup_file>.dump.gz | gzip -dc | pg_restore -C -d postgres"

# 配置恢復目標時間點
cat > /var/lib/postgresql/data/recovery.conf << EOF
restore_command = 'cp ${WAL_DIR}/%f %p'
recovery_target_time = '${RESTORE_TARGET}'
recovery_target_action = 'promote'
EOF

# 啟動 PostgreSQL
docker-compose start db

# 監控恢復進度
docker logs -f db
```

恢復完成後，執行資料完整性檢查，確認數據正確後啟動其他服務。

### 4.4 復原程序：NAS 設備更換

當 NAS 設備完全損壞需更換新設備時，完整的復原流程如下：

**準備階段**：取得新 NAS 設備（相同或相容型號）、確認外接硬碟備份或雲端備份可用、準備系統安裝媒體與程式碼。

**環境重建階段**：安裝 QTS 作業系統並完成基礎配置、建立與原設備相同配置的 RAID 陣列、安裝 Docker 與 Docker Compose、複製程式碼與配置檔案至新設備。

**服務恢復階段**：建立必要的目錄結構（/opt/ai-investor、/storage_data、/backup_data）、從 config 備份恢復 docker-compose.yml 與 .env、從 config 備份恢復 nginx、prometheus、grafana 配置、從 pg_dump 備份恢復資料庫、從 storage 備份恢復非結構化數據、啟動所有服務並驗證功能正常。

**驗證確認階段**：執行功能測試確認所有模組正常、驗證數據完整性與正確性、通知用戶系統已恢復。

### 4.5 復原程序：勒索軟體應變

若遭受勒索軟體攻擊，應變程序如下：

**隔離階段**：立即切斷 NAS 網路連線、停止所有 Docker 容器、識別受影響的檔案範圍。

**評估階段**：確認哪些檔案被加密、評估備份是否受到影響、決定是否可以犧牲部分數據從備份恢復。

**清除階段**：識別並清除勒索軟體、進行病毒掃描確認系統潔淨、變更所有密碼與 API 金鑰。

**恢復階段**：若本地備份未被加密，從本地備份恢復；若本地備份受影響，使用外接硬碟備份或雲端備份恢復；必要時從頭重建系統。

**強化階段**：安裝並啟用 NAS 防毒軟體、加強網路安全配置、審查並改進安全政策、考慮部署勒索軟體偵測解決方案。

## 第五章：備份維護管理

### 5.1 備份狀態監控

備份任務的執行狀態納入監控系統追蹤。監控項目包括：備份任務是否按時執行、備份任務執行耗時、備份檔案大小與增長趨勢、備份驗證結果。Alertmanager 配置備份相關告警規則：

```yaml
- alert: BackupFailed
  expr: backup_job_status{job="pg_backup"} == 0
  for: 5m
  labels:
    severity: critical
  annotations:
    summary: "資料庫備份失敗"
    description: "PostgreSQL 備份任務執行失敗，請立即檢查"

- alert: BackupVerificationFailed
  expr: backup_verify_status == 0
  for: 1m
  labels:
    severity: warning
  annotations:
    summary: "備份驗證失敗"
    description: "備份檔案驗證未通過，可能影響災復能力"

- alert: BackupOld
  expr: time() - backup_last_success_time > 172800  # 48小時
  for: 1h
  labels:
    severity: warning
  annotations:
    summary: "備份過舊"
    description: "超過 48 小時無成功備份，請檢查備份系統"
```

### 5.2 備份容量管理

備份儲存容量需要持續監控與管理。隨著時間推移，備份檔案會持續累積，需確保儲存空間足夠。備份容量估算如下：pg_dump 全量備份（每日）預估 2-5GB、WAL 歸檔（每日）預估 1-2GB、配置檔案備份（每日）預估 50MB、Storage 資料備份（每日增量）預估 100-500MB。總計每日新增備份資料約 3.2-7.5GB，7 天本地備份需預估 25-60GB 儲存空間。

容量監控腳本定期執行並發出告警：

```bash
#!/bin/bash
# /opt/ai-investor/backup/scripts/check_backup_space.sh

BACKUP_DIR="/backup_data"
MAX_USAGE=80

USAGE=$(df ${BACKUP_DIR} | tail -1 | awk '{print $5}' | sed 's/%//')

if [ ${USAGE} -gt ${MAX_USAGE} ]; then
    echo "WARNING: Backup directory disk usage is ${USAGE}%"
    # 發送告警
    curl -X POST "https://notify.example.com/alert" \
        -d "message=備份目錄空間使用率達 ${USAGE}%"
fi
```

### 5.3 災復演練計畫

災復演練是驗證備份策略有效性的關鍵活動。本計畫規定以下演練頻率與類型：

每季度執行一次「模擬災復演練」，在測試環境中模擬完整災復流程，驗證備份檔案可恢復性、復原程序文件完整性、團隊熟悉復原流程。演練前需通知所有相關人員、選擇業務低峰時段、準備詳細檢核清單。演練後需檢討並更新復原程序、記錄發現的問題並追蹤改善。

每年執行一次「全量災復演練」，在隔離環境中從頭重建完整系統，驗證異地備份可用性、跨媒體恢復能力、文檔與腳本的完整性。演練結果納入年度資訊安全稽核報告。
