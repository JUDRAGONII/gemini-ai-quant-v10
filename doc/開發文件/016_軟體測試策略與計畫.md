## 第一章：測試策略總覽

### 1.1 測試目標與範疇

AI 投資分析儀 V10.0 的軟體測試策略旨在確保系統在全生命週期中維持高品質標準，作為專業金融軟體，系統的正確性、可靠性與安全性至關重要。測試策略採用測試金字塔模型，依據投入產出效益配置各層級測試的比重，確保在有限的測試資源下最大化品質保障效果。測試範疇涵蓋前端應用、後端 API、資料庫、數據處理管線、AI 引擎等所有系統元件。

本策略的核心目標包括：確保系統功能符合規格書定義的業務需求、確保系統效能符合效能需求規格、確保系統在各種異常情境下仍能正確運作、確保系統資料的正確性與完整性、確保系統符合資訊安全要求、確保系統變更不會破壞既有功能（回歸測試）。測試活動貫穿軟體開發生命週期，從需求階段即開始規劃測試案例，確保測試覆蓋所有功能路徑。

### 1.2 測試金字塔模型

測試金字塔描述不同層級測試的數量比例關係，由底層至頂層分別為：單元測試、整合測試、API 測試、端對端測試。理想的測試金字塔應該是寬闊的底座（大量單元測試）支撐中等寬度的主體（適量整合測試），頂端為尖細的頂峰（少量端對端測試）。此配置反映了不同層級測試的投資報酬率：單元測試執行快速、隔離性好、維護成本低，適合測試大量細節；端對端測試貼近真實使用情境，但執行慢、維護成本高，應精選關鍵路徑測試。

本系統的測試金字塔配置如下：單元測試佔 70%，目標覆蓋率為 80% 以上，測試對象為各函式與類別的業務邏輯；整合測試佔 20%，目標為所有資料庫操作、外部服務呼叫皆經過測試；端對端測試佔 10%，目標為所有核心使用者情境皆經過自動化測試。此配置確保測試套件執行時間控制在可接受範圍內（單元測試 < 5 分鐘，整合測試 < 15 分鐘，端對端測試 < 30 分鐘），支援持續整合流程。

### 1.3 測試環境架構

測試環境採用與生產環境一致或高度相似的架構，確保測試結果的可信度。本系統配置三種測試環境：

開發環境（Development）供開發人員日常開發與快速驗證使用，執行單元測試與部分整合測試。環境配置為單機 Docker Compose，所有服務運行於同一主機，資料庫使用 SQLite 或 PostgreSQL 測試實例。開發環境可頻繁重建，不保留正式數據。

測試環境（Staging）供測試人員執行完整測試與回歸測試使用，執行所有層級的自動化測試與手動測試。環境配置為完整 Docker Compose 架構，資料庫使用 PostgreSQL，資料使用經過脫敏處理的正式數據副本。測試環境定期從生產環境同步數據。

預 生 產 環 境（Pre-Production）為生產環境的精確鏡像，用於發布前的最終驗證與效能測試。環境配置與生產環境完全一致，包括硬體規格、網路配置、資料庫規模等。預 生 產 環境禁止進行破壞性測試。

## 第二章：測試類型與方法

### 2.1 單元測試

單元測試是測試金字塔的基礎，針對系統中最小的可測試單元（函式、方法、類別）進行隔離測試。單元測試的原則包括：每個測試只驗證一個行為、測試之間相互獨立不依賴、測試執行不涉及外部依賴（資料庫、網路、檔案系統）、測試執行快速（毫秒級）。本系統的單元測試框架選用 pytest（Python）與 Jest（JavaScript）。

單元測試覆蓋的重點領域包括：業務邏輯層（計算邏輯、轉換邏輯、驗證邏輯）、資料存取層（查詢建構、資料映射）、工具函式（字串處理、日期處理、數學計算）。以下為單元測試範例：

```python
# tests/unit/test_quant_factors.py

import pytest
from app.services.quant.factors import (
    calculate_pe_ratio,
    calculate_momentum,
    calculate_composite_score
)

class TestCalculatePERatio:
    """測試本益比計算"""
    
    def test_normal_pe_ratio(self):
        """正常本益比計算"""
        price = 100.0
        eps = 5.0
        result = calculate_pe_ratio(price, eps)
        assert result == pytest.approx(20.0, rel=1e-4)
    
    def test_zero_eps_raises_error(self):
        """EPS 為零時拋出例外"""
        price = 100.0
        eps = 0.0
        with pytest.raises(ValueError, match="EPS cannot be zero"):
            calculate_pe_ratio(price, eps)
    
    def test_negative_eps_handled(self):
        """負 EPS 正確處理"""
        price = 100.0
        eps = -5.0
        result = calculate_pe_ratio(price, eps)
        assert result == pytest.approx(-20.0, rel=1e-4)


class TestCalculateMomentum:
    """測試動能因子計算"""
    
    def test_positive_momentum(self):
        """正動能計算"""
        prices = [100, 102, 105, 108, 110]
        result = calculate_momentum(prices, period=3)
        assert result > 0
    
    def test_negative_momentum(self):
        """負動能計算"""
        prices = [110, 108, 105, 102, 100]
        result = calculate_momentum(prices, period=3)
        assert result < 0
    
    def test_insufficient_data(self):
        """數據不足時拋出例外"""
        prices = [100, 102]
        with pytest.raises(ValueError, match="Insufficient price data"):
            calculate_momentum(prices, period=5)
```

### 2.2 整合測試

整合測試驗證多個元件組合後的正確性，重點測試元件之間的互動。整合測試的原則包括：測試真實的依賴元件（真實資料庫連線、真實快取服務）、隔離外部服務（使用 testcontainers 或 mock 外部 API）、確保測試環境隔離（每個測試套件使用獨立的測試資料庫）。本系統使用 pytest 配合 testcontainers-py 或 SQLAlchemy 的測試 mixin 進行整合測試。

整合測試覆蓋的重點領域包括：資料庫操作（CRUD 作業、交易處理、查詢效能）、外部 API 整合（數據提供商的 API 呼叫、AI 模型 API 呼叫）、快取操作（Redis 的讀寫、过期策略）、工作流執行（Prefect flow 的執行與狀態追蹤）。以下為整合測試範例：

```python
# tests/integration/test_market_data_repository.py

import pytest
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
from app.db.models import Base, StockPrice
from app.db.repositories import StockPriceRepository

@pytest.fixture(scope="module")
def test_engine():
    engine = create_engine("postgresql://test:test@localhost:5432/test_db")
    Base.metadata.create_all(engine)
    yield engine
    Base.metadata.drop_all(engine)

@pytest.fixture(scope="module")
def test_session(test_engine):
    Session = sessionmaker(bind=test_engine)
    session = Session()
    yield session
    session.rollback()
    session.close()

@pytest.fixture
def repository(test_session):
    return StockPriceRepository(test_session)

@pytest.fixture
def sample_price_data():
    return [
        StockPrice(
            stock_code="2330",
            trade_date="2026-01-15",
            open_price=100.0,
            high_price=102.0,
            low_price=99.0,
            close_price=101.0,
            volume=5000000
        ),
        StockPrice(
            stock_code="2330",
            trade_date="2026-01-16",
            open_price=101.0,
            high_price=103.0,
            low_price=100.5,
            close_price=102.5,
            volume=5200000
        )
    ]

def test_repository_create(repository, sample_price_data):
    """測試建立價格資料"""
    result = repository.create(sample_price_data[0])
    assert result.id is not None
    assert result.stock_code == "2330"

def test_repository_get_by_code_and_date(repository, sample_price_data):
    """測試依代碼與日期查詢"""
    repository.create(sample_price_data[0])
    result = repository.get_by_code_and_date("2330", "2026-01-15")
    assert result is not None
    assert result.close_price == 101.0

def test_repository_get_price_history(repository, sample_price_data):
    """測試取得價格歷史"""
    for price in sample_price_data:
        repository.create(price)
    
    results = repository.get_price_history("2330", days=10)
    assert len(results) == 2
```

### 2.3 API 測試

API 測試驗證 RESTful API 端點的行為正確性，包括請求處理、響應格式、錯誤處理與認證授權。API 測試使用 pytest 配合 requests 庫或 FastAPI 的 TestClient。以下為 API 測試範例：

```python
# tests/api/test_stocks_api.py

import pytest
from fastapi.testclient import TestClient
from app.main import app

@pytest.fixture
def client():
    return TestClient(app)

@pytest.fixture
def auth_headers():
    return {"Authorization": "Bearer test_api_key"}

def test_get_stock_list(client, auth_headers):
    """測試取得股票清單"""
    response = client.get("/api/v1/stocks", headers=auth_headers)
    assert response.status_code == 200
    data = response.json()
    assert "data" in data
    assert "meta" in data
    assert data["meta"]["page"] == 1

def test_get_stock_prices(client, auth_headers):
    """測試取得個股行情"""
    response = client.get(
        "/api/v1/stocks/2330/prices",
        headers=auth_headers,
        params={"start_date": "2026-01-01", "end_date": "2026-01-31"}
    )
    assert response.status_code == 200
    data = response.json()
    assert data["status"] == "success"
    assert "prices" in data["data"]

def test_get_stock_quote(client, auth_headers):
    """測試取得即時報價"""
    response = client.get("/api/v1/stocks/2330/quote", headers=auth_headers)
    assert response.status_code == 200
    data = response.json()
    assert "price" in data["data"]
    assert "change_percent" in data["data"]

def test_invalid_stock_code(client, auth_headers):
    """測試無效股票代碼"""
    response = client.get("/api/v1/stocks/INVALID_CODE/quote", headers=auth_headers)
    assert response.status_code == 404
    assert response.json()["error"]["code"] == "40401"

def test_unauthorized_access(client):
    """測試未授權存取"""
    response = client.get("/api/v1/stocks")
    assert response.status_code == 401

def test_rate_limit_exceeded(client, auth_headers):
    """測試速率限制"""
    for _ in range(61):
        response = client.get("/api/v1/stocks", headers=auth_headers)
    assert response.status_code == 429
```

## 第三章：測試資料管理

### 3.1 測試資料策略

測試資料是測試活動的基礎，好的測試資料策略能確保測試的有效性與效率。本系統採用以下測試資料策略：

測試資料分類為：空白資料集（用於驗證邊界與錯誤處理）、標準資料集（預定義的標準測試數據，用於回歸測試）、隨機資料集（大量生成的隨機數據，用於效能測試與壓力測試）、正式數據副本（經過脫敏的正式環境數據，用於整合測試）。

測試資料產生方式包括：Factory 模式（使用工廠類別產生測試資料）、Fixture 檔案（從 JSON/YAML 檔案載入預定義資料）、測試資料生成服務（測試時即時生成所需的數據）。每個測試類別應有對應的 fixture，確保測試資料的一致性與可重用性。

### 3.2 資料庫測試配置

測試資料庫配置為測試隔離的基礎。開發環境使用 SQLite 進行單元測試，確保測試執行速度：

## 第四章：測試自動化

### 4.1 持續整合流程

測試自動化是持續整合（CI）的核心。本系統的 CI 流程設計如下：

提交觸發（On Push）：開發人員推送程式碼至版本庫，CI 流程自動觸發，執行以下測試：單元測試（全部）、程式碼風格檢查（lint）、類型檢查（type check）、安全性掃描（dependency check）。

PR 審查觸發（On Pull Request）：建立 PR 時 CI 執行完整測試套件，產生測試報告並回傳至 PR，測試失敗阻擋 PR 合併。

合併主分支觸發（On Merge to Main）：PR 合併後 CI 執行完整測試並部署至測試環境，執行自動化端對端測試，產生發布候選版本。

### 4.2 CI 配置範例

```yaml

```

### 4.3 測試報告產生

測試報告是測試活動的重要產出，用於記錄測試結果並支援決策。本系統產生以下測試報告：

測試執行報告（Test Execution Report）：記錄每次測試執行的結果統計，包括：通過/失敗/跳過數量、測試執行時間、覆蓋率統計、失敗測試清單與錯誤訊息。

程式碼覆蓋率報告（Code Coverage Report）：使用 pytest-cov 產生，顯示各模組的覆蓋率，識別未經測試覆蓋的程式碼區塊。

API 文件整合（API Documentation）：使用 OpenAPI 測試框架產生 API 測試報告，整合至 Swagger UI 顯示。

## 第五章：效能測試

### 5.1 效能測試策略

效能測試驗證系統在正常負載與壓力負載下的行為表現。本系統的效能測試類型包括：

負載測試（Load Testing）：驗證系統在預期負載下的效能表現。預期負載為 2 位用戶同時使用，API 請求率約 60 rpm（每分鐘）。測試持續時間為 30 分鐘，驗證效能指標穩定。

壓力測試（Stress Testing）：驗證系統的最大承載能力與失效模式。測試場景為逐漸增加負載至系統瓶頸，識別系統的最大吞吐量與失效點。

浸泡測試（Soak Testing）：驗證系統在長時間持續負載下的穩定性。測試持續時間為 24 小時，監控記憶體泄漏、資源耗盡等問題。

### 5.2 效能測試工具與場景

本系統使用 Locust 進行效能測試：

## 第六章：資安測試

### 6.1 資安測試範疇

資安測試確保系統符合資訊安全需求。本系統的資安測試類型包括：

滲透測試（Penetration Testing）：模擬攻擊者視角的攻擊測試，測試項目包括：身份認證繞過、權限提升、SQL 注入、XSS 跨站腳本、API 金鑰洩漏。滲透測試每季度執行一次，由專業資安團隊執行或使用自動化工具（如 OWASP ZAP）。

依賴漏洞掃描（Dependency Vulnerability Scanning）：掃描第三方依賴套件的已知漏洞。使用工具：Safety、OWASP Dependency-Check、Snyk。每週自動執行，發現高危漏洞時發出告警。

靜態程式碼安全分析（SAST）：分析程式碼中的安全漏洞。使用工具：Bandit（Python）、Semgrep。自動整合至 CI 流程。

動態程式碼安全分析（DAST）：執行中的應用程式進行安全測試。使用工具：OWASP ZAP API Scan。整合至 CI 流程，在測試環境執行。

### 6.2 OWASP ZAP 整合範例

```yaml
# .github/workflows/security.yml

name: Security Scan

on:
  schedule:
    - cron: '0 0 * * 0'  # 每週執行
  pull_request:
    branches: [main]

jobs:
  zap-scan:
    runs-on: ubuntu-latest
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Set up Python

      - name: Upload ZAP Report

      - name: Cleanup
        run: |
          docker-compose -f docker-compose.test.yml down -v
```

## 第七章：測試度量與品質門檻

### 7.1 測試度量指標

測試活動需要量化評估，本系統追蹤以下測試度量指標：

測試覆蓋率指標：程式碼行覆蓋率（Line Coverage）、分支覆蓋率（Branch Coverage）、函式覆蓋率（Function Coverage）、類別覆蓋率（Class Coverage）。目標值：整體行覆蓋率 > 80%，核心模組 > 90%。

測試執行指標：測試執行數量（Passed/Failed/Skipped）、測試執行時間、測試穩定率（Flaky Test Rate）。目標值：穩定率 > 99%。

缺陷指標：缺陷密度（每千行程式碼的缺陷數）、缺陷發現率、缺陷修復率、平均缺陷修復時間。

### 7.2 品質門檻

| 指標 | 閾值 | 說明 |
|------|------|------|
| 單元測試覆蓋率 | >= 80% | 整體程式碼行覆蓋率 |
| 核心模組覆蓋率 | >= 90% | 金融計算、AI 推理等核心模組 |
| API 測試覆蓋率 | 100% | 所有公開 API 端點 |
| 測試穩定率 | >= 99% | 非預期失敗的測試比例 |
| 漏洞發現數 | 0 高危 | 高危漏洞數必須為零 |
| 效能回應時間 | P99 < 500ms | API P99 回應時間 |

品質門檻為 CI 流程的品質關卡（Quality Gate），未通過門檻的變更不得合併至主分支。
