## 二、任務一：投資組合完整 CRUD 功能（T-AI-001）

### 2.1 任務概述

**任務編號**：T-AI-001
**任務名稱**：投資組合完整 CRUD 功能開發
**優先級**：P1
**預估工時**：8 人天
**負責人員**：前端開發 2 人、後端開發 1 人
**開始日期**：第 3 週第 4 天
**結束日期**：第 4 週第 5 天

### 2.2 需求說明

投資組合管理功能是用戶追蹤和管理個人投資的核心功能。系統需支援用戶建立多個投資組合，每個投資組合可包含多個持股部位，並自動計算投資報酬率與績效指標。

後端資料庫需設計 user_portfolios 和 user_holdings 兩個資料表，儲存投資組合的基本資訊與持股明細。前端需開發投資組合列表頁面、詳情頁面、表單頁面，並整合績效分析圖表。

API 端點需涵蓋：建立投資組合（POST）、查詢投資組合列表（GET）、查詢投資組合詳情（GET）、更新投資組合（PUT）、刪除投資組合（DELETE）、新增持股部位（POST）、更新持股部位（PUT）、刪除持股部位（DELETE）、計算投資報酬率（GET）等功能。

### 2.3 工作分解

**後端開發（第 3-4 天）**：

第 3 天的工作重點是資料庫設計與後端 API 基礎建設。首先，設計 user_portfolios 和 user_holdings 的資料表結構，欄位包括：投資組合 ID、用户 ID、投資組合名稱、說明、創建時間、更新时间；持股部位則包含：股票代碼、股票名稱、買入日期、買入價格、股數、手續費、稅金等欄位。接著，在 PostgreSQL 中建立對應的資料表，並設計適當的索引以優化查詢效能。最後，實作投資組合 CRUD API，確保每個端點都能正確處理請求並返回標準格式的響應。

第 4 天的工作重點是持股部位 API 與績效計算邏輯。實作持股部位的 CRUD API，支援新增、查詢、更新、刪除操作。開發投資報酬率計算邏輯，計算方法包括：絕對報酬率（（目前價值 - 總成本）/ 總成本）、相對報酬率（與大盤比較）、各持股對整體報酬的貢獻度。實作績效曲線計算，支援依日、周、月維度查詢歷史績效。

**前端開發（第 5-8 天）**：

第 5-6 天的工作重點是投資組合列表頁面與詳情頁面基礎框架。投資組合列表頁面需顯示：用戶所有投資組合的卡片式展示、每個投資組合的總價值與報酬率、點擊進入詳情頁面的連結、支援新增投資組合的按鈕。詳情頁面框架需包含：投資組合基本資訊區、績效曲線圖區、持股部位列表區、動作按鈕區。

第 7 天的工作重點是新增/編輯投資組合表單與持股管理介面。開發新增投資組合的表單，包含名稱、說明等欄位。開發編輯投資組合的表單，支援修改基本資訊。開發新增持股的表單，包含股票代碼、買入日期、價格、股數等欄位。開發編輯持股的表單，支援更新買入資訊。

第 8 天的工作重點是績效分析圖表與整合測試。整合 Recharts 或 Chart.js 繪製績效曲線圖，支援日、周、月視圖切換。計算並顯示：總報酬金額、總報酬率、勝率（正報酬交易日比例）、最大回撤等指標。執行前端整合測試，確保各頁面與組件間的資料流通正確。

### 2.5 資料庫 Schema 設計

```sql
-- user_portfolios 資料表
CREATE TABLE user_portfolios (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES auth.users(id),
    name VARCHAR(100) NOT NULL,
    description TEXT,
    currency VARCHAR(3) DEFAULT 'TWD',
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    
    CONSTRAINT fk_user FOREIGN KEY (user_id) REFERENCES auth.users(id)
);

CREATE INDEX idx_portfolios_user ON user_portfolios(user_id);

-- user_holdings 資料表
CREATE TABLE user_holdings (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    portfolio_id UUID NOT NULL REFERENCES user_portfolios(id) ON DELETE CASCADE,
    stock_code VARCHAR(20) NOT NULL,
    stock_name VARCHAR(100),
    buy_date DATE NOT NULL,
    buy_price DECIMAL(18, 4) NOT NULL,
    shares DECIMAL(18, 4) NOT NULL,
    commission DECIMAL(18, 2) DEFAULT 0,
    tax DECIMAL(18, 2) DEFAULT 0,
    notes TEXT,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    
    CONSTRAINT fk_portfolio FOREIGN KEY (portfolio_id) REFERENCES user_portfolios(id)
);

CREATE INDEX idx_holdings_portfolio ON user_holdings(portfolio_id);
CREATE INDEX idx_holdings_stock ON user_holdings(stock_code);
```

### 2.6 驗收標準

**功能驗收標準**：

用戶可建立新的投資組合，名稱為必填項目。建立成功後，投資組合會出現在列表中。點擊投資組合可進入詳情頁面，顯示完整的投資組合資訊。用戶可編輯投資組合的基本資訊，變更會正確儲存。用戶可刪除投資組合，系統會要求二次確認。用戶可在投資組合中新增持股，系統會驗證輸入資料的正確性。用戶可編輯已存在的持股資訊。系統會自動計算並顯示投資組合的目前總價值。系統會自動計算並顯示投資報酬率（絕對報酬與相對報酬）。績效曲線圖會正確顯示投資組合的歷史績效走勢。

**非功能驗收標準**：

API 響應時間 P95 < 300ms。前端頁面載入時間 < 3 秒。單元測試覆蓋率 > 80%。整合測試覆蓋所有 API 端點。響應式設計相容 Desktop 與 Tablet。

## 三、任務二：RAG 語義搜尋 UI（T-AI-002）

### 3.1 任務概述

**任務編號**：T-AI-002
**任務名稱**：語義搜尋頁面開發
**優先級**：P1
**預估工時**：5 人天
**負責人員**：前端開發人員
**開始日期**：第 4 週第 1 天
**結束日期**：第 5 週第 3 天

### 3.2 需求說明

RAG 語義搜尋功能允許用戶使用自然語言搜尋 AI 投資報告知識庫。用戶輸入問題或關鍵字，系統會返回相關的報告片段，並顯示語義相似度分數。

此功能需整合後端的 match_reports RPC 函數，前端負責提供友善的搜尋介面，包括搜尋輸入框、搜尋結果列表、相似度分數顯示、報告詳情展開等功能。頁面設計需符合系統的 Glassmorphism 風格，並確保載入狀態的適當顯示。

### 3.3 工作分解

**第 1 天：UI 設計與基礎框架**

分析現有的 RAG API 與資料結構，確認前端需要處理的資料格式。設計語義搜尋頁面的 UI 配置，包含搜尋輸入區、結果列表區、篩選選項區。創建頁面基礎框架與組件結構。

**第 2 天：搜尋輸入介面**

實作搜尋輸入框，支援文字輸入與 Enter 鍵觸發搜尋。添加搜尋按鈕，顯示載入狀態。開發最近搜尋記錄功能，使用 localStorage 儲存。實作清除搜尋功能。

**第 3 天：搜尋結果展示**

呼叫後端 API 執行語義搜尋。設計搜尋結果列表的卡片式佈局，顯示報告標題、股票代碼、相似度分數、摘要內容。實作相似度分數的視覺化顯示（如進度條或顏色標示）。添加展開/收合功能，顯示完整報告內容或摘要。

**第 4 天：互動功能與優化**

添加結果排序功能，可依相似度或日期排序。實作分頁或無限卷軸載入。開發熱門搜尋關鍵字提示功能。優化載入狀態顯示，加入骨架屏（Skeleton Screen）。

**第 5 天：整合測試與除錯**

執行各瀏覽器相容性測試。修復發現的 UI 問題。補充單元測試。文件編寫。

### 3.4 驗收標準

**功能驗證項目**：

搜尋輸入框可正常輸入文字。點擊搜尋按鈕或按下 Enter 鍵可觸發搜尋。系統正確呼叫後端 API 並返回結果。搜尋結果以卡片式佈局正確顯示。每個結果顯示語義相似度分數。點擊結果可展開查看完整摘要。支援結果排序（按相似度、日期）。載入狀態正確顯示。頁面響應式顯示正確。

**品質標準**：

搜尋結果載入時間 < 2 秒。單元測試覆蓋率 > 80%。跨瀏覽器相容性（Chrome 90+, Firefox 90+）。頁面符合系統設計風格。

## 四、任務三：AI 報告頁面優化（T-AI-003）

### 4.2 需求說明

現有的 AI 報告頁面功能基本完整，但需要優化用戶體驗，包括：版面配置調整以提升閱讀舒適度、評分圖表的互動功能增強、載入體驗優化減少用戶等待焦慮。

優化後的報告頁面應提供清晰的資訊層次，讓用戶能夠快速獲取關鍵資訊，同時提供深入了解的入口。

### 4.3 工作分解

調整報告各區塊的間距與比例。優化標題層級與字體大小。改善數據展示的可讀性。調整色彩搭配符合系統風格。

**第 3 天：評分圖表互動**

為評分雷達圖添加互動功能，滑鼠懸停顯示詳細數值。開發評分趨勢圖，展示評分歷史變化。添加評分比較功能，支援與產業平均或大盤比較。

**第 4 天：載入體驗優化**

分析頁面載入瓶頸，針對性優化。添加適當的載入動畫與骨架屏。實作資料預載入邏輯。

**第 5 天：測試與修復**

跨瀏覽器測試。收集用戶回饋進行微調。補充測試案例。

### 4.4 驗收標準

報告版面清晰易讀，資訊層次分明。評分圖表支援互動顯示。載入時間 < 3 秒。響應式顯示正確。無明顯 UI 問題。

### 6.2 測試環境

測試環境使用獨立的測試資料庫，確保測試資料隔離。Mock 外部 API 依賴，確保測試穩定性。CI Pipeline 自動執行測試，測試失敗阻擋合併。

### 7.1 識別風險

### 7.2 應變計畫

若後端 API 無法按時完成，前端開發人員將使用 Mock 資料繼續開發，確保功能邏輯正確，待 API 完成後再替換為實際資料。若 RAG API 效能不佳，將添加載入狀態提示用戶，並考慮後端快取機制。
